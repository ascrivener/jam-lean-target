# PVM differential harness

This harness compares jam-lean's PVM (Ψ, GP v0.8.0 Appendix A) with PolkaVM, the reference that
produced the official PVM test vectors. It works at the PVM level, below the block-level fuzzer.

Both sides read the same testcases, in the koute/jamtestvectors `pvm/programs` format (schema
`pvm/schema.asn`: program blob, initial pc and gas, and `map` / `write` / `set-reg` / `run` /
`assert` steps). A testcase is a `.json` file, or one line of a `.jsonl` file. Each side has two
modes:

* `run` prints each testcase back with every `assert` replaced by the state actually observed:
  status, registers, pc, gas, page-fault address, host call and non-zero memory.
* `check` compares against the given asserts.

| Side | Program | What runs |
| --- | --- | --- |
| Lean | `lake exe pvmrun run\|check FILE\|DIR…` (`PvmRun.lean`) | `PVM.psi`; compiled code runs the proved-equal `PVM.psiFast` (`@[csimp]`). Imports only jam-lean's `PVM` library. |
| Reference | `tools/pvm-ref/target/release/pvm-ref run\|check FILE\|DIR…` (`cargo build --release` in `tools/pvm-ref`) | PolkaVM 0.38.1 (crates.io) interpreter |

`python3 scripts/pvmdiff.py INPUT… --out DIR` runs both sides and compares every assert. It writes
`DIR/divergences.jsonl` and prints a summary by case family and by differing field.

## Reference setup (matches PolkaVM's `spectool`)

The official vectors were generated by `tools/spectool` in paritytech/polkavm. `pvm-ref` uses the
same setup:

* interpreter backend, dynamic paging;
* a strict module, synchronous (per-block) gas metering, step tracing, and cost model
  `Full(L2Hit)`;
* the raw program blob, as `ProgramParts::empty(JamV1).code_and_jump_table`. For the `JamV1` ISA
  this is exactly the GP deblob format E(|j|) ⌢ E₁(z) ⌢ E(|c|) ⌢ E_z(j) ⌢ c ⌢ E(k);
* `map` uses `zero_memory_with_memory_protection`, `write` unprotects read-only pages for the
  write, and `pc` is the last stepped instruction (also on halt).

Differences in setup, all reported and never hidden:

* **Blob refused at load.** Status `load-error`. GP v0.8.0 then has Ψ panic before any step, with
  gas unchanged. When Ψ does exactly that, the case counts as agreeing ("both reject").
* **Out-of-range jump-table entries.** Strict mode refuses them at load. GP v0.8.0 checks a
  jump-table entry only when a jump uses it. Such cases are re-run non-strict and marked
  `strict-error` (shown as `(lax)` in the summary).
* **Pages below 2¹⁶** cannot be mapped in PolkaVM; the reference reports `ref-crash`.
* **Host-call ids** are u32 in PolkaVM; GP v0.8.0 sign-extends the immediate to 64 bits.
* **After ∎ or ☇**, both runners drop any later `run` step.

## Results (2026-11-15, PolkaVM 0.38.1)

36,839 generated cases (default seed). One run takes Lean 5.3 s and PolkaVM 2.9 s.
36,500 agree, including 998 where PolkaVM refuses the blob and Ψ panics before any step. Block
costs ϱ^Δ agree at every block start of every program both sides load.

Every divergence falls into one of these classes:

| | Class | Minimal case | Ψ (GP v0.8.0) | PolkaVM | Reading |
| --- | --- | --- | --- | --- | --- |
| D1 | three-register r_D octet ≥ 16 | `add_64` r7, r8, octet 16 | ω₁₂ (min(12, 16)) | ω₀ (16 mod 16) | follows GP #554 |
| D2 | jump-table entry size z > 4 | z = 5, no entries | runs | load error | follows GP #559 |
| D3 | `ecalli` id with bit 31 set | `ecalli` −1 | 2⁶⁴ − 1 (𝒳) | 2³² − 1 (u32) | representation |
| D4 | last instruction can fall off the end (branch, `fallthrough`) | code [`fallthrough`] | panic after charging the block | load error | see triage |
| D5 | store straddling a read-only page into an unmapped one | `store_u16` at 0x21FFF | fault 0x21000 (min x) | fault 0x22000 | see triage |
| D6 | z = 0 with entries | `jump_ind` to j₀ = 0 | jumps to 0 | panic | see triage |
| D7 | out-of-range jump-table entry, unused | | runs | strict: load error | setup; agree when non-strict |
| D8 | pages below 2¹⁶ | | | cannot map | setup; not compared |

Verdicts (parent session, against pvm.tex v0.8.0): Ψ is right in D4, D5 and D6. D1 and D2 follow
later GP changes. D3, D7 and D8 come from representation or setup. All exported vectors carry the
GP v0.8.0 result (Ψ's).

### Where D4–D6 reach a JAM node (GP v0.8.0)

Any service can deploy such a blob, or pass it to `machine`. Compilers don't emit them.

* **Ψ_M** (`pvm.tex` §A.8) runs service code for is-authorized, refine and accumulate. It returns
  u = ϱ − max(ϱ′, 0) and ☇/∞/output.
  * **D4**: Ψ charges the block, then panics: u = ϱ^Δ of the first block, result ☇. If an
    implementation treats a refused blob as ☇ without charging (as when deblob = ∇), u = 0.
  * **D6**: Ψ loops until ∞: u = all the gas, result ∞. PolkaVM gives ☇, with u equal to one
    block's cost.
  * Accumulation: u feeds the accumulation statistics (π_S), and so the state root.
  * Refine: u and the result (∞ vs ☇) go into the work digest, and so into the work-report hash.
  * Is-authorized: the result decides whether the package is authorized.
  * **D5** at Ψ_M level: F ends Ψ_M as ☇ with the same u, so the fault address is not visible.
* **Inner PVMs** (`pvm_invocations.tex`, Ω_M `machine` l.~590, Ω_E `invoke` l.~680). These run
  in refine only; their effect is on the work report.
  * **D4**: `machine` returns HUH only when deblob(p, i) = ∇. A D4 blob deblobs fine, so the
    service gets a handle. An implementation that validates as PolkaVM does would return HUH
    instead, and ω′₇ goes into the service's registers.
  * **D5**: `invoke` returns FAULT with ω′₈ = x, the page address. 0x21000 vs 0x22000 is visible
    to the calling service.
  * **D6**: `invoke` returns OOG vs PANIC, and different gas.

### Newest PolkaVM

0.38.1 is the newest crates.io release and was the head of polkavm master on 2026-11-15.

The node-relevant recompiler backend was also tried, with `POLKAVM_REF_BACKEND=compiler
POLKAVM_REF_STATIC=1`. The static memory map is needed because dynamic paging needs userfaultfd,
which this container forbids. D4 and D6 behave the same there: the blob is refused (validation at
offset 0), and z = 0 panics. D5 needs `map` steps, which work only with dynamic paging, so it was
not tested on the recompiler.

## Exported vectors

`vectors/pvm/` holds 1,408 vectors with GP v0.8.0 results. They are the agreeing edge cases plus
every D1–D6 case. `vectors/pvm/README.md` lists them by class. CI runs `pvmrun check vectors/pvm`,
which takes 0.2 s.
